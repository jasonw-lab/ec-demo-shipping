# ADR-008: Backend Go 認証・認可技術 — QA

## 2026-02-10T21:02 指摘者： Gemini 2.5 Pro

### 構造・記述の整合性

- Q1: **ADR番号がAGENT.mdのADR一覧に未登録**
AGENT.md（セクション「ADR (Architecture Decision Records)」）にADR-007, ADR-008が記載されていない。ADR-006までしか登録されていないため、AGENT.mdを更新すべき。

- Q2: **Section 5.3 サービス間認証のコードブロック言語指定が不適切**
`\`\`\`go` と指定されているが、内容はJSON構造体であり、Goコードではない。`\`\`\`json` に修正すべき。

- Q3: **JWT構造の `roles` と `permissions` の両方をペイロードに含める設計の根拠が不明**
Section 4.1 のJWT構造にて `roles` と `permissions` の両方を含めている。一般的にRBACでは、ロールからパーミッションを導出するか、パーミッションを直接付与するかのどちらかを選択する。両方を含める設計意図（例: パフォーマンス最適化のため事前展開する、ロール単位とパーミッション単位の両方で認可判定を行うなど）を明記すべき。

### セキュリティ設計

- Q4: **Refresh Tokenの保管場所・仕組みの記載がない**
Section 5.1 でRefresh Tokenの有効期限（7日）を定義しているが、Refresh Tokenの保管場所（サーバーサイドDB / Redis / クライアントSecure Cookie等）、発行フロー（Token Rotation含む）、失効時の挙動が記載されていない。ADRレベルで方針を定めるべき。

- Q5: **CORS設定に関する言及がない**
Admin UIからAPIへのリクエストはクロスオリジンになる可能性が高い。CORS設定の方針（許可オリジン、プリフライトリクエストの取り扱い等）について触れるべき。

- Q6: **Rate Limiting / Brute Force 対策の記載がない**
認証エンドポイント（トークン発行）に対するブルートフォース攻撃やDoS対策について言及がない。セキュリティ考慮事項として方針を記載すべき。

### アーキテクチャ・運用

- Q7: **公開鍵の配布メカニズムが未定義**
Section 5.1 でRS256（非対称鍵）を採用と決定しているが、各サービスへの公開鍵の配布方法（JWKS エンドポイント / 設定ファイル / 環境変数等）が記載されていない。マイクロサービス環境では JWKS（JSON Web Key Set）エンドポイントが一般的であるため、方針を明記すべき。

- Q8: **Auth Server（認証サーバー）の責務と所在が曖昧**
Section 2 Option B の図で「Auth Server」が登場するが、これが自前実装なのか、外部IdP（Keycloak等）なのか、API Gateway の一部なのかが明確でない。Phase 1 での具体的な方針を記載すべき。MVP段階でどこまでを自前実装するかの判断は重要。

- Q9: **Webhook（外部API）の認証方式が未定義**
Section 1 の背景で「外部API: 配送業者連携、Webhook など」を要件に挙げているが、Section 3 の決定ではWebhookの認証方式（Signature検証 / Shared Secret / OAuth等）に言及がない。

### ADR-004との整合性

- Q10: **ADR-004の改善提案「Middlewareディレクトリの追加」との関係性**
ADR-004 のSection「改善提案」でMiddlewareディレクトリの追加が提案されている（`internal/middleware/`）。ADR-008の4.3で同じディレクトリ構成を定義しているが、ADR-004の提案を受けた決定である旨の相互参照がない。トレーサビリティのために明記すべき。

### 将来の拡張

- Q11: **マルチテナント対応の深掘りが不足**
JWT構造に `tenant_id` を含めているが、テナントに基づくデータ分離や認可の方針（テナント横断アクセスの制御など）が記載されていない。RBAC定義にテナント概念がどう影響するかの方針を明記すべき。
