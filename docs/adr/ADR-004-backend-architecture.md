# ADR-004: Backendフォルダ構成とアーキテクチャ

## ステータス
承認 - 2026年2月3日

## コンテキスト
Go言語を使用したShipping Serviceのバックエンド実装において、保守性・拡張性・テスタビリティを確保するための適切なフォルダ構成を決定する必要がある。

クリーンアーキテクチャの原則に基づき、以下の要件を満たす必要がある：
- ドメインロジックとインフラストラクチャの分離
- 依存関係の方向性の制御（外層から内層への依存）
- テスタビリティの確保
- Go言語の標準プラクティスへの準拠

## 決定

### 採用するフォルダ構成

```
apps/api/
├── cmd/                    # アプリケーションエントリーポイント
│   ├── server/            # メインAPIサーバー
│   │   └── main.go
│   └── dbinit/            # データベース初期化ツール
│       └── main.go
├── internal/              # プライベートアプリケーションコード
│   ├── domain/           # ドメイン層（エンティティ、ビジネスルール）
│   ├── service/          # アプリケーション層（ユースケース）
│   ├── handler/          # インターフェース層（HTTPハンドラー）
│   ├── infra/            # インフラストラクチャ層
│   │   ├── database/     # データベース接続
│   │   ├── repository/   # データ永続化
│   │   └── kafka/        # メッセージング
│   └── config/           # 設定管理
├── scripts/              # スクリプト類
├── go.mod
└── go.sum
```

### レイヤー構成と依存関係

#### 1. Domain Layer（最内層）
- **場所**: `internal/domain/`
- **責務**: エンティティ定義、ビジネスルール
- **依存**: なし（他のどのレイヤーにも依存しない）
- **例**: `Shipping`エンティティ、ドメインバリデーション

#### 2. Application/Service Layer
- **場所**: `internal/service/`
- **責務**: ユースケースの実装、ビジネスロジックの調整
- **依存**: Domain Layer
- **例**: `ShippingService`（配送作成、ステータス更新）

#### 3. Interface/Handler Layer
- **場所**: `internal/handler/`
- **責務**: HTTPリクエスト/レスポンスの処理、ルーティング
- **依存**: Service Layer
- **例**: REST APIエンドポイント、リクエストバリデーション

#### 4. Infrastructure Layer（最外層）
- **場所**: `internal/infra/`
- **責務**: 外部システムとの統合
- **依存**: Domain Layer（インターフェース実装）
- **サブディレクトリ**:
  - `database/`: DB接続、マイグレーション
  - `repository/`: データ永続化の実装
  - `kafka/`: メッセージング実装

#### 5. Configuration Layer
- **場所**: `internal/config/`
- **責務**: 環境変数、設定ファイルの管理
- **依存**: なし

### エントリーポイント構成

#### `cmd/` ディレクトリ
複数の実行可能ファイルを管理：
- `cmd/server/`: メインAPIサーバー
- `cmd/dbinit/`: データベース初期化ツール

各ディレクトリは独立した`main.go`を持ち、必要な依存関係を組み立てる。

## 根拠

### 1. Go標準プラクティスの採用
- `internal/`: 外部パッケージからのインポートを防ぐGo言語の機能を活用
- `cmd/`: 複数の実行可能ファイルを明確に分離
- フラットな構造: 深いネストを避け、Goのシンプルさを維持

### 2. クリーンアーキテクチャの適用
- **依存性逆転の原則**: インフラ層がドメイン層のインターフェースを実装
- **単一責任の原則**: 各レイヤーが明確な責務を持つ
- **テスタビリティ**: モックやスタブを用いた単体テストが容易

### 3. 保守性と拡張性
- **明確な境界**: レイヤー間の責務が明確に分離
- **低結合**: レイヤー間の依存が最小限
- **高凝集**: 関連するコードが同じディレクトリに配置

### 4. チーム開発への適合
- **ディレクトリ名の明確性**: `handler`、`service`、`repository`など、一般的な用語を使用
- **パッケージ構造の直感性**: 新規メンバーが理解しやすい
- **並行開発の容易性**: レイヤーごとに独立した開発が可能

## 現状の評価と改善提案

### ✅ 現在実装されている構造（良好）
- Domain、Service、Handler、Infraの明確な分離
- インターフェース定義による依存性の制御
- テストファイルの適切な配置

### 🔄 改善提案

#### 1. **DTO（Data Transfer Object）レイヤーの追加**
```
internal/
├── dto/                  # リクエスト/レスポンスDTO
│   ├── request/
│   │   └── shipping_request.go
│   └── response/
│       └── shipping_response.go
```

**理由**: 
- APIリクエスト/レスポンスとドメインエンティティを分離
- APIバージョニングの容易化
- バリデーションルールの集約

#### 2. **Middlewareディレクトリの追加**
```
internal/
├── middleware/           # HTTPミドルウェア
│   ├── auth.go
│   ├── logger.go
│   └── response/
```

**理由**: 
- APIリクエスト/レスポンスとドメインエンティティを分離
- APIバージョニングの容易化
- バリデーションルールの集約

#### 2. **Middlewareディレクトリの追加**
```
internal/
├── middleware/           # HTTPミドルウェア
```

**理由**:
- 横断的関心事の集約（認証、ログ、CORS、エラーハンドリング）
- 再利用可能なHTTPミドルウェアの統一管理

#### 3. **Utilsディレクトリの追加**
```
internal/
├── utils/               # 共通ユーティリティ
```

**理由**:
- 共通機能の再利用（エラーハンドリング、バリデーション、レスポンスヘルパー）
- コードの重複削減

#### 4. **pkg/ディレクトリの検討**
```
apps/api/
├── pkg/                 # 外部公開可能なライブラリ
│   └── errors/         # カスタムエラー型
```

**理由**:
- 他のマイクロサービスと共有可能なコード
- 将来的なモノレポ構成への対応

#### 5. **テストディレクトリの整理**
```
apps/api/
├── test/                # 統合テスト、E2Eテスト
│   ├── integration/
│   ├── fixtures/       # テストデータ
│   └── mocks/          # モックオブジェクト
```

**理由**:
- 単体テストと統合テストの明確な分離
- テストデータの一元管理

#### 6. **ドキュメントの追加**
```
apps/api/
├── docs/               # API仕様書
```

**理由**:
- API仕様の明確化（Swagger/OpenAPI）」を示す
- Domainレイヤーは他に依存しない
- InfraレイヤーはDomainのインターフェースを実装

## 代替案

### 代替案1: Feature-Based構成
```
internal/
├── shipping/
│   ├── domain.go
│   ├── service.go
│   ├── handler.go
│   └── repository.go
```

**却下理由**: 
- 小規模プロジェクトには適しているが、複数機能が増えた際にレイヤー間の依存関係が不明瞭になる
- テストやモックの配置が複雑化

### 代替案2: Hexagonal Architecture（Ports & Adapters）
```
internal/
├── core/
│   └── ports/
├── adapters/
│   ├── primary/
│   └── secondary/
```

**却下理由**:
- Goコミュニティでは一般的でない用語
- オーバーエンジニアリングのリスク

## 影響

### プラス影響
- ✅ 新機能追加時の影響範囲が明確
- ✅ レイヤーごとの単体テストが容易
- ✅ 技術スタックの変更が容易（例：DBの変更）
- ✅ チームメンバーのオンボーディングが容易

### マイナス影響
- ⚠️ 小規模な変更でも複数ファイルの修正が必要になる場合がある
- ⚠️ レイヤー間のインターフェース定義に初期コストがかかる

### 移行コスト
現在の構造は既に推奨構造とほぼ一致しているため、移行コストは最小限：
1. DTO層の追加: 2-3日
2. Middleware層の追加: 1-2日
3. テストディレクトリの整理: 1日
