## ⚠️ 懸念点・リスク

### 1. Issue 010: ダッシュボード

#### 🔴 高リスク
**「SHIPPED TODAY（本日出荷）」の定義が曖昧**
- 「本日出荷」の判定基準が不明確（UTCベース？ローカルタイム？）
- タイムゾーン処理が必要だが、既存API（Issue 005で実装）に時刻フィルタ機能があるか不明
- **推奨対応**: 
  - 「本日」の定義を明記（例: JST 00:00〜23:59にステータスがSHIPPEDに変更されたもの）
  - APIに `updated_at` 範囲検索機能が必要
  - フロントエンドでの日付処理ライブラリ選定（date-fns推奨）
- **✅ 最終対策**:
  - 「本日」= JST基準 00:00:00〜23:59:59 で確定
  - API: `GET /api/v1/shipments?shipped_from=2026-01-25T00:00:00+09:00&shipped_to=2026-01-25T23:59:59+09:00` を追加
  - フロントエンド: `date-fns` + `date-fns-tz` を導入、タイムゾーン変換は `formatInTimeZone()` で統一
  - Issue 010 仕様書に「本日出荷の定義」セクションを追記する

#### 🟡 中リスク
**要対応発送リストの優先順位ロジックが未定義**
- 「優先対応が必要な発送」の判定基準が記載されていない
- 想定: CREATED の古い順？RETURNED？SLA違反？
- **推奨対応**: 優先度ルールを明記（例: RETURNED → CREATED（24h経過）→ READY（古い順））
- **✅ 最終対策**:
  - 優先度ルール確定: ① RETURNED（全件）→ ② CREATED（作成後24h超過）→ ③ READY（更新日時の古い順）
  - API: `GET /api/v1/shipments/priority?limit=5` 新規エンドポイント追加
  - バックエンドでソート済みデータを返却（フロントエンドでのソート不要）
  - Issue 010 仕様書に優先度ルールを明記する

**KPIカード遷移時のURL設計**
- フィルタ付き遷移の実装方法（Query Parameters? State管理?）
- ブラウザバック時の挙動を考慮する必要がある
- **推奨対応**: URL Query Parameters方式（`/shipments?status=RETURNED`）で実装
- **✅ 最終対策**:
  - URL設計確定: `/shipments?status={STATUS}&date={DATE}` 形式
  - Next.js `useSearchParams()` + `useRouter()` で実装
  - ブラウザバック対応: URL変更時に `replace` ではなく `push` を使用し履歴を保持
  - 初期表示時はURLパラメータを読み取りフィルタ状態を復元

### 2. Issue 011: 発送一覧

#### 🔴 高リスク
**一括操作のトランザクション処理が未定義**
- 複数行選択時のステータス一括変更で、一部失敗時のロールバック戦略が不明
- 楽観ロックとの整合性（既存はバージョン管理している）
- **推奨対応**:
  - 一括更新APIの仕様策定（全成功 or 全失敗 vs 部分成功）
  - UIでの結果表示設計（例: 「10件中8件成功、2件失敗」）
  - 失敗時のリトライ機能
- **✅ 最終対策**:
  - トランザクション戦略: **部分成功方式**を採用（業務継続性優先）
  - API: `PATCH /api/v1/shipments/bulk` レスポンス形式:
    ```json
    {
      "success": [{"id": 1, "status": "SHIPPED"}],
      "failed": [{"id": 2, "error": "VERSION_CONFLICT", "message": "..."}]
    }
    ```
  - UI: 結果サマリをToastで表示、失敗行はテーブル上でハイライト
  - 失敗行の「再試行」ボタンを提供（最新データ取得後に再実行）
  - 楽観ロック: 各行のversionを送信、競合時は409を個別返却

**CSVエクスポートのデータ範囲**
- 表示中ページのみ？全データ？選択行のみ？
- 大量データ時のパフォーマンス（Issue外としているが影響大）
- **推奨対応**: 
  - 初期実装は「選択行のみ」に限定
  - 全データエクスポートは別Issueで検討
- **✅ 最終対策**:
  - Phase 1: 選択行のみエクスポート（クライアントサイド生成、最大100件制限）
  - Phase 2（別Issue）: 全データエクスポート（サーバーサイド生成、非同期ダウンロード）
  - 出力形式: UTF-8 BOM付きCSV（Excel互換）
  - カラム: 注文ID, ステータス, 配送業者, 追跡番号, 配送先, 更新日時
  - ファイル名: `shipments_export_YYYYMMDD_HHmmss.csv`

#### 🟡 中リスク
**ソート機能とページネーションの競合**
- サーバーサイドソートが必要だが、既存API（Issue 003）にソート機能があるか確認が必要
- クライアントサイドソートでは大量データに対応不可
- **推奨対応**: API仕様を確認し、ソートパラメータ追加が必要か判断
- **✅ 最終対策**:
  - 既存API確認結果: ソート機能なし → 追加が必要
  - API拡張: `GET /api/v1/shipments?sort=updated_at&order=desc`
  - 対応カラム: `order_id`, `status`, `updated_at`（Issue 011仕様通り）
  - デフォルト: `updated_at desc`（最新順）
  - TanStack Table の `manualSorting: true` でサーバーサイドソート連携

**フィルタチップ表示の情報量**
- 複数フィルタ適用時のUI設計（例: ステータス3件 + 配送業者2件）
- 画面の横幅制約を考慮
- **推奨対応**: 最大表示数を決める（例: 5件まで、それ以上は「+2」表示）
- **✅ 最終対策**:
  - 最大表示: 4件まで個別表示、5件以上は「+N」バッジで省略
  - 各チップに×ボタンで個別解除可能
  - 「すべてクリア」リンクで一括リセット
  - レスポンシブ対応: モバイル幅では2件まで表示、残りは折りたたみ

### 3. Issue 012: 発送詳細

#### 🔴 高リスク
**ステータスタイムラインの実現可能性**
- 既存DBスキーマに各ステータスの遷移日時が保存されているか不明
- 監査ログから復元する場合、パフォーマンス懸念
- **推奨対応**:
  - DBスキーマ確認（`created_at`, `shipped_at`, `delivered_at` カラムの有無）
  - なければマイグレーション計画が必要
  - 監査ログとの二重管理を避ける設計
- **✅ 最終対策**:
  - DB確認結果: `created_at`, `updated_at` のみ存在 → **監査ログから復元方式を採用**
  - 理由: カラム追加は既存データのマイグレーションが複雑、監査ログは既に実装済み
  - API: `GET /api/v1/shipments/{id}/timeline` 新規エンドポイント
    - 監査ログから `status` 変更履歴を抽出し、タイムライン形式で返却
  - パフォーマンス対策: 監査ログにインデックス追加 `(shipping_id, created_at)`
  - キャッシュ: 変更がない限り304を返却（ETag使用）

**外部追跡リンクの業者別URL管理**
- 配送業者ごとにURL形式が異なる（ヤマト、佐川、日本郵便など）
- URLテンプレート管理が必要だが、仕様に記載なし
- **推奨対応**:
  - マスタデータとして業者別URL定義を追加
  - フロントエンドで動的生成（例: `https://track.yamato.jp/{tracking_number}`）
- **✅ 最終対策**:
  - 配送業者マスタをフロントエンド定数として定義:
    ```typescript
    export const CARRIER_TRACKING_URLS: Record<string, string> = {
      YAMATO: 'https://toi.kuronekoyamato.co.jp/cgi-bin/tneko?number={tracking_number}',
      SAGAWA: 'https://k2k.sagawa-exp.co.jp/p/web/okurijosearch.do?okurijoNo={tracking_number}',
      JAPANPOST: 'https://trackings.post.japanpost.jp/services/srv/search?requestNo1={tracking_number}',
    };
    ```
  - 追跡リンクは `target="_blank" rel="noopener noreferrer"` で新規タブ表示
  - 未対応業者の場合はリンク非表示（追跡番号のみ表示）

#### 🟡 中リスク
**監査ログの表示件数制限**
- 長期運用で監査ログが膨大になった場合の表示方法が未定義
- **推奨対応**: 最新N件表示 or ページネーション
- **✅ 最終対策**:
  - 初期表示: 最新10件
  - 「もっと見る」ボタンで追加10件ずつ読み込み（無限スクロールは不採用、明示的な操作を優先）
  - API: `GET /api/v1/shipments/{id}/audit-logs?limit=10&offset=0`
  - 総件数をレスポンスヘッダー `X-Total-Count` で返却

**追跡番号コピー機能のブラウザ互換性**
- Clipboard API（`navigator.clipboard.writeText()`）はHTTPS必須
- 開発環境での動作確認が必要
- **推奨対応**: フォールバック実装を用意
- **✅ 最終対策**:
  - 実装: `navigator.clipboard.writeText()` を優先使用
  - フォールバック: `document.execCommand('copy')` （非推奨だが互換性のため）
  - 共通フック `useCopyToClipboard()` を作成し、成功/失敗をToastで通知
  - 開発環境（localhost）でも動作確認済み（Clipboard APIはlocalhostをSecure Contextとして扱う）

**返送処理の業務フロー**
- 「返送処理」ボタンの実行後、ステータスがRETURNEDになるだけか、他の処理が必要か不明
- 倉庫への返送指示など、後続業務との連携が未定義
- **推奨対応**: 返送処理の詳細フローを別途定義
- **✅ 最終対策**:
  - 本Issue範囲: ステータスを `RETURNED` に変更するのみ（シンプル実装）
  - 返送処理ボタン押下時:
    1. 確認ダイアログ表示（「返送処理を実行しますか？」）
    2. `PATCH /api/v1/shipments/{id}` で `status: RETURNED` に更新
    3. 監査ログに記録（実行者: operator）
  - 後続業務連携（倉庫指示、返金処理など）は別Issue（Issue 013以降）で対応
  - Issue 012 仕様書に「返送処理は本Issueではステータス変更のみ」と明記
